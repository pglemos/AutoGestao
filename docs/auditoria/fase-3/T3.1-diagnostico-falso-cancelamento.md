## Problema

Commits que alteram apenas documentação geravam deploys cancelados pela Vercel — comportamento
desejado. Porém o mecanismo padrão de comparação (GitHub compare API entre `prev` e `cur`) falhava
em cenários de clone raso, causando deploys indevidos ou decisões incorretas.

## Causas raiz identificadas (experimentos executados)

| # | Causa | Evidência |
|---|---|---|
| 1 | GitHub **não permite** `git fetch origin <sha>` — refs por SHA são rejeitados ("couldn't find remote ref") | `fetchCommitObject` retornou `false` em todos os clones de teste |
| 2 | `git fetch --shallow-exclude=<prev>` remove o objeto do clone quando o commit é raso | `hasCommitLocally(prev)` → `false` |
| 3 | `VERCEL_GIT_REPO_SLUG` **não contém o owner** — montar `owner/slug` apenas com o slug gerava HTTP 404 na API GitHub | Logs de build anteriores |

## Corretude atual do script (pós-fix)

Camadas de resolução em `resolveChangedFiles`:
1. `diffFilesLocally` — se `prev` e `cur` existem no clone (diff puro, 3-way).
2. `fetchCommitObject(prev)` com `--depth=1` — tenta trazer só o objeto (falha no GitHub, catch → `false`).
3. `unshallowBranch` com `git fetch --depth=3 origin main` — aprofunda o clone o suficiente para o `prev` mais próximo (20s timeout); retorna `hasCommitLocally(prev)`.
4. `diffFilesViaApi` — fallback via GitHub compare API com slug `owner/slug` (6s timeout via AbortController).

Regra de segurança: **qualquer falha de inspeção → build obrigatório** (nunca suprimir deploy).
